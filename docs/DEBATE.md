## Brand Strategist

### R1 — positioning

Headline เดิม *"คนสาย IT ที่เขียนโค้ดและสร้างระบบ — และกำลังเอา AI มาทำให้งานเดิมเสร็จเร็วขึ้น"* มีปัญหาโครงสร้างสองชั้น ชั้นแรกคือ "คนสาย IT" ซึ่งเป็นหมวดหมู่ ไม่ใช่จุดยืน — HR อ่านแล้วยังต้องเดาต่อว่าจ้างทำอะไรได้ ชั้นที่สองหนักกว่า คือคำว่า **"กำลัง"** ซึ่งเปลี่ยนประโยคจากผลลัพธ์เป็นความตั้งใจ คนอ่านที่มีเวลา 5 วินาทีจะจับได้ว่านี่คือคนที่ยังไม่เสร็จ

Bio ย่อหน้า 3 มีของดีที่สุดในไฟล์ — "AI agent หลายตัวที่แบ่งหน้าที่กันชัดเจน ประสานงานผ่านเอกสารและ PR แทนที่จะคุยกันในแชทเดียว" — นั่นคือจุดต่าง แต่มันถูกฝังไว้ย่อหน้าที่ 3 ของหน้า About ซึ่งคนส่วนใหญ่อ่านไม่ถึง

เสนอ Headline: **"เขียนโค้ดและออกแบบระบบ — ใช้ AI เร่งงาน แต่ยังส่งต่อให้คนอื่นทำต่อได้"** ท่อนหลังคือสิ่งที่คู่แข่งพูดไม่ได้ เพราะส่วนใหญ่ขายความเร็วอย่างเดียว

### R2 — Interests

`## Interests` ทั้ง 4 ข้อเขียนด้วยคำนามลอย ๆ ("AI agents และการใช้ AI ช่วยเขียนโค้ด") ซึ่งไม่ได้บอกว่าจ้างแล้วได้อะไร ผมไม่ได้อยากให้เปลี่ยนโครงสร้างข้อมูล — แค่เขียนใหม่เป็น **`หัวข้อ — คำขยายที่เป็นผลลัพธ์`** เช่น "Automation — ลดงานซ้ำที่กินเวลาโดยไม่ได้สร้างอะไรใหม่" หน้าเว็บจะ split ที่ `—` เองได้ สัญญา `string[]` ไม่ต้องเปลี่ยน

ตอบ UX: ผมไม่เห็นด้วยที่จะยุบหน้า Interests ทิ้ง มันคือหน้าเดียวที่แปลง "สนใจ" เป็น "จ้างได้" ถ้ายุบไปอยู่ในหน้าแรก มันจะกลายเป็นรายการ bullet ที่ไม่มีใครอ่าน

### R3 — Contact / Guestbook

CTA ต้องมีอันเดียว คือ **ฟอร์ม contact** อีเมลแบบ `mailto:` เปล่า ๆ ทั้งโดน scrape และทำให้คนที่อ่านบนมือถือหลุดออกจากเว็บไปแอปอีเมล แล้วไม่กลับมา

Guestbook — ผมยอมรับข้อโต้แย้งของ Devil ตั้งแต่ยังไม่ทันเถียง สำหรับเว็บที่คนดูคือ HR การมีสมุดเยี่ยมว่างเปล่า หรือแย่กว่านั้นคือมีสแปมสองข้อความ มันทำลายความน่าเชื่อถือมากกว่าที่จะเพิ่ม **ผมถอน Guestbook ออกจาก Must**

### R4 — ความน่าเชื่อถือ

Bio ย่อหน้า 3 มีประโยค "ทำให้งานตรวจสอบย้อนหลังได้" ซึ่งถ้าเขียนบนเว็บแบบลอย ๆ จะกลายเป็นคำสัญญาที่พิสูจน์ผิดได้ ควรผูกกับขอบเขต เช่น "ตัดสินใจอะไรไว้ ตามย้อนได้จากเอกสาร" ไม่ใช่ "ทุกอย่างตรวจสอบย้อนหลังได้"

ส่วนที่ Devil เสนอให้ตัดเรื่อง AI ทิ้งเพื่อความปลอดภัย ผมไม่เห็นด้วย — ถ้าตัดจุดต่างเดียวที่มีทิ้ง สิ่งที่เหลือคือ CV ที่เหมือนคนอื่นทุกใบ ความเสี่ยงของการไม่ถูกจำได้ สูงกว่าความเสี่ยงของการถูกมองว่าตามกระแส

### R5 — ขอบเขต

สิ่งที่ต้องได้ใน v1 มีแค่: หน้าแรกที่ตอบ "นี่ใคร จ้างทำอะไรได้" · About ที่เล่าจุดต่าง · Interests ที่เป็นผลลัพธ์ · Contact ที่ส่งได้จริง

**สรุปข้อเสนอ 3 ข้อของบทบาทนี้**

1. เปลี่ยน Headline ให้จบที่ผลลัพธ์ ไม่ใช่ความตั้งใจ — ตัดคำว่า "กำลัง" ทิ้งทั้งไฟล์
2. เขียน `## Interests` ใหม่เป็น `หัวข้อ — คำขยาย` โดยไม่แตะสัญญาข้อมูล
3. โครงเรื่อง About ใช้มุม **B (ทำให้ AI หลายตัวทำงานร่วมกันได้)** เป็นแกน แล้วปิดท้ายด้วยมุม **C (ส่งงานจบ)** — ตรงกับที่ `## Brainstorm` เสนอไว้

## UX Critic

### R1 — หน้าแรกตอนนี้

ผมอ่าน `docs/PROFILE.md` คู่กับสิ่งที่หน้าเว็บ render จริง แล้วเจอปัญหาที่ใหญ่กว่าเรื่อง copy: **หน้าแรกพิมพ์บรรทัด `Audience:` ออกไปให้คนดูเห็น** (`src/pages/index.astro:13`) แปลว่าผู้เยี่ยมชมจะเห็นข้อความทำนอง "HR และคนที่กำลังพิจารณาจ้างงาน รวมถึงลูกค้า..." บนหน้าแรก

`Audience` คือ *โน้ตภายในว่าเรากำลังเขียนถึงใคร* ไม่ใช่เนื้อหาสำหรับผู้อ่าน การแสดงมันออกไปเท่ากับบอกคนดูว่า "คุณคือเป้าหมายการตลาดของฉัน" และถ้า HR เปิดดู มันประกาศว่าเจ้าของกำลังหางานอยู่ ซึ่งเจ้าของอาจไม่ได้ตั้งใจให้นายจ้างปัจจุบันเห็น

ปัญหาเดียวกันซ่อนอยู่ใน `FALLBACK.audience` (`src/lib/profile.ts`) ที่เป็น `Hiring managers / peers / community` — ถ้าหัวข้อใน PROFILE ว่างเมื่อไหร่ ค่านี้จะขึ้นเว็บแทนทันที ต้องแก้ทั้งสองจุด ไม่ใช่จุดเดียว

### R2 — IA สำหรับ 4 หน้า

โครง Home / About / Interests / Contact ใช้ได้ ข้อมูลใน PROFILE พอสำหรับทั้ง 4 หน้าแล้ว แต่มีสองจุดที่ยังไม่พร้อม

จุดแรก Bio มี 4 ย่อหน้า แต่หน้าเว็บใส่ไว้ในแท็กเดียว ทำให้บรรทัดว่างหายไปตอน render — กลายเป็นกำแพงตัวอักษรก้อนเดียว (บันทึกไว้แล้วเป็น L5)

จุดที่สอง nav มี 4 ลิงก์เท่ากันหมด ทั้งที่ Contact คือปลายทางที่เราอยากให้ไป ควรให้ Contact เด่นกว่าอีกสามอันด้วยน้ำหนัก ไม่ใช่ด้วยขนาดหรือสีที่ตะโกน

ตอบ Brand: ผมไม่ได้จะยุบหน้า Interests — ผมจะบอกว่าถ้าเนื้อหาในนั้นยังเป็น bullet ลอย หน้านั้นจะไม่มีเหตุผลให้อยู่ ถ้าเขียนใหม่แบบที่คุณเสนอ ผมเห็นด้วยให้เก็บไว้

### R3 — Guestbook คือปัญหา UX ก่อนจะเป็นปัญหาความปลอดภัย

ตอนนี้ `/api/guestbook` ยังเป็น stub ที่ throw ออกมา แล้วหน้าเว็บเอา `data.error` ไปแสดงตรง ๆ ผลคือผู้เยี่ยมชมเห็นข้อความ `NOT_IMPLEMENTED: listGuestbook — Lab 05 OpenCode` เต็ม ๆ บนหน้าจอ

สองเรื่องในนั้นแย่คนละแบบ — เรื่องแรกคือ **ชื่อคอร์สหลุดออกหน้าเว็บ** ซึ่งเป็นสิ่งที่ guardrail ของเราตั้งใจกัน แต่ `tests/public-site.test.ts` สแกนแค่ markup ที่เขียนไว้ในไฟล์ จับข้อความที่มาจาก API ตอน runtime ไม่ได้ เรื่องที่สองคือ error ของระบบไม่ใช่ภาษาที่คนอ่านรู้เรื่อง

หน้า Contact ก็เป็นแบบเดียวกัน (`src/pages/contact.astro:36` แสดง `Error: <ข้อความดิบจาก API>`)

microcopy ที่ควรเป็น: 501 → "ฟอร์มยังไม่เปิดใช้งาน" · 400 → "กรอกข้อมูลไม่ครบ ลองตรวจอีกครั้ง" · 500 → "ส่งไม่สำเร็จ ลองใหม่อีกครั้ง"

### R4 — a11y และการส่งต่อลิงก์

ลิงก์เว็บนี้จะถูกส่งต่อทางแชทและอีเมล แปลว่า title/description ต่อหน้าไม่ใช่เรื่อง SEO อย่างเดียว แต่คือสิ่งที่คนเห็นก่อนกดด้วย · ขั้นต่ำที่ต้องผ่าน: ลำดับ heading ถูกต้อง (h1 เดียวต่อหน้า) · focus ที่มองเห็นได้ตอนกด Tab · contrast ผ่าน AA · ฟอร์มมี label จริงไม่ใช่ placeholder แทน label

### R5 — เกณฑ์ปิดงาน

ผมขอเกณฑ์ที่วัดได้ ไม่ใช่ "ดูดีแล้ว": เปิดหน้าแรกแล้วไม่เห็นคำว่า Audience · Bio แสดงครบ 4 ย่อหน้า · ทุกหน้ามี title/description ของตัวเอง · ฟอร์ม Contact มีสถานะกำลังส่ง/สำเร็จ/ผิดพลาด เป็นภาษาคน

## Devil's Advocate

### R1 — ความเสี่ยงข้อ 1: ประกาศว่ากำลังหางาน

ต่อจาก UX — บรรทัด `Audience:` บนหน้าแรกไม่ใช่แค่ awkward มันคือข้อมูลที่ใช้ต่อได้จริง นายจ้างปัจจุบันหรือเพื่อนร่วมงานที่เจอลิงก์นี้ อ่านได้ทันทีว่าเจ้าของกำลังมองหางานใหม่ และหน้าเว็บไม่มีทางรู้ว่าใครเปิดดู **นี่คือ P0 ไม่ใช่เรื่องความสวยงาม**

### R2 — ความเสี่ยงข้อ 2: Guestbook คือ XSS ที่รออยู่

`src/pages/guestbook.astro:29` ต่อ HTML จาก `e.name` และ `e.message` เข้า `innerHTML` โดยไม่ escape อะไรเลย ตอนนี้มันยังไม่ระเบิดเพราะ `listGuestbook` ยัง throw อยู่ — แปลว่า **ความปลอดภัยของเว็บนี้ตอนนี้ขึ้นอยู่กับการที่ฟีเจอร์ยังพังอยู่** วินาทีที่ Lab 05 ทำให้ backend ทำงาน ใครก็ได้ที่ส่งข้อความมีแท็ก `<script>` จะรันสคริปต์ในเบราว์เซอร์ของทุกคนที่เปิดหน้านั้น รวมถึง HR ที่เจ้าของส่งลิงก์ไปให้

ข้อเสนอผมคือ v1 **ไม่เปิดให้เขียน** และเอาออกจาก nav ถ้าจะเก็บหน้าไว้ก็ต้องเลิกใช้ `innerHTML` ก่อนทุกกรณี ไม่ใช่รอให้ backend เสร็จแล้วค่อยแก้ — เพราะถึงตอนนั้นจะไม่มีใครจำได้

ตอบ Brand ที่ถอน Guestbook ออกจาก Must เอง: ดี แต่ยังไม่พอ **การไม่ลิงก์จาก nav ไม่ได้แปลว่าหน้านั้นเข้าไม่ได้** ต้องปิดที่โค้ดด้วย

### R3 — ความเสี่ยงข้อ 3: อีเมลตัวอย่างหลุดขึ้นเว็บจริง

`## Contact` ใน PROFILE ตอนนี้เป็น `demo@example.com` ซึ่งถูกต้องสำหรับตอนพัฒนา แต่ถ้ามันหลุดขึ้นเว็บจริงตอน ship คนที่อยากติดต่อจะส่งเข้าที่ที่ไม่มีใครอ่าน แล้วเจ้าของจะไม่มีทางรู้เลยว่าพลาดงานไป ควรมีเกณฑ์ชัดว่าอีเมลตัวอย่างห้ามอยู่บนหน้าเว็บที่ deploy — ช่องทางเดียวคือฟอร์ม

### R4 — ความเสี่ยงข้อ 4: เปิดลิงก์ GitHub = เปิดโฟลเดอร์ docs ทั้งโฟลเดอร์

`## Contact` เว้น `github:` กับ `linkedin:` ไว้ และ `## Brainstorm` บอกว่าจะเปิดทีหลัง — ผมขอค้านว่าอย่าเพิ่งเปิดจนกว่าจะตอบได้ว่า repo นี้จะเป็น public หรือ private

เพราะถ้า repo public แล้วลิงก์จากหน้าเว็บ คนที่กดเข้าไปจะอ่าน `docs/` ได้ทั้งหมด **รวมถึงหัวข้อ `## ไม่เผยแพร่บนเว็บ` ที่ระบุเป็นลายลักษณ์อักษรว่าอะไรที่เจ้าของไม่อยากให้เห็น** และหัวข้อ `## Brainstorm` ที่มีเนื้อหาเชิงกลยุทธ์ การมีรายการ "ห้ามเผยแพร่" ที่เผยแพร่อยู่ มันแย่กว่าไม่มีรายการเลย

### R5 — ความเสี่ยงข้อ 5: overclaim และ scope creep

**Overclaim** — "ตรวจสอบย้อนหลังได้" และการพูดถึง AI agent หลายตัว ถ้าเขียนแบบไม่มีตัวอย่างประกอบ คนที่รู้จริงจะถามทันทีว่า "แล้วผลงานอยู่ไหน" ตอนนี้ยังไม่มี case study สักชิ้น ทางออกคือเขียนให้แคบและจริง ไม่ใช่เขียนให้ดูใหญ่

**Scope creep** — สิ่งที่ต้องตัดจาก Must ตั้งแต่วันนี้: Guestbook (ย้ายไป Later) · analytics ทุกชนิดใน v1 (เก็บ IP เงียบ ๆ คือปัญหา privacy ที่ไม่มีใครขอ) · blog/CMS · dark mode · i18n

**คำถามที่ต้องตอบก่อน ship**

1. repo นี้จะ public หรือ private — ถ้า public เนื้อหาใน `docs/` ยอมให้ใครก็อ่านได้จริงไหม
2. ถ้ามีคนส่งข้อความผ่านฟอร์ม ใครอ่าน และข้อความเก็บไว้นานแค่ไหน
3. deploy แล้วข้อมูลใน SQLite อยู่รอดไหม (ไม่ mount volume = หายทุกครั้งที่ deploy)
4. ถ้านายจ้างปัจจุบันเปิดเว็บนี้วันนี้ มีบรรทัดไหนที่เจ้าของจะเสียใจ

## ประเด็นที่ยังไม่ปิดในรอบนี้ (ส่งต่อให้ DECISIONS)

- เก็บหน้า Guestbook ไว้แบบอ่านอย่างเดียว หรือเอาออกจาก v1 ทั้งหน้า — Brand เอนไปทาง "เอาออก" · Devil ยอมรับได้ทั้งสองแบบถ้าเลิกใช้ `innerHTML`
- ระดับความละเอียดของมุมเล่าเรื่อง B — เล่าเรื่อง AI agent มากแค่ไหนถึงจะไม่กลายเป็น overclaim
- repo public/private — ต้องให้เจ้าของตัดสิน ไม่ใช่ agent
